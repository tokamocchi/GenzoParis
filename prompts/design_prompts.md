# 写真現像・カタログ管理ツール 検討・設計用プロンプト集

Lightroom Classic 相当の写真現像・カタログ管理ツールを自作するにあたり、
AI に機能検討・技術選定・設計を段階的に依頼するためのプロンプトです。

## 使い方

1. まず **[0] 前提条件シート** の `【】` を埋める（記入済みのものは [premise_sheet.md](premise_sheet.md)）。分からない項目は「未定」のままで OK です（AI に提案させます）。
2. **[1]〜[6] を順番に**、同じ会話（またはプロジェクト）で投げる。各フェーズの冒頭に前提条件シートを貼り付けると、会話が分かれても使えます。
3. 各フェーズの出力をレビューし、決定事項を「決定事項ログ」（末尾テンプレート）に追記してから次へ進む。
4. 前フェーズの成果物を次のプロンプトの `{{前フェーズの成果物}}` に貼り付ける。

> ⚠ AI の出力に含まれる **ライセンス条件・対応機種数・性能値・ライブラリのバージョンや保守状況** は誤りや古い情報を含む可能性があります。採用判断の前に、必ず公式情報・実測で確認してください。

```
あなたはデスクトップアプリ、画像処理、GPU プログラミングに詳しいシニアアーキテクトです。

{{前提条件シート}}

## これまでの決定事項
{{[1][2] の成果物}}

## 依頼
以下の各レイヤーについて技術候補を比較し、推奨案を提示してください。

| レイヤー | 検討候補の例（これ以外も歓迎） |
|---|---|
| アプリ形態 / UI | Tauri + Web UI、Electron、Qt 6、Rust ネイティブ GUI（egui / Slint / iced）、Flutter、OS ネイティブ |
| コア言語 | Rust、C++、TypeScript + ネイティブモジュール、Python（試作のみ） |
| RAW デコード | LibRaw、RawSpeed、rawler、DNG SDK |
| デモザイク | AMaZE、RCD、LMMSE、VNG 等（ライブラリ内蔵か自前か） |
| 現像パイプライン実行 | GPU コンピュート（wgpu / WebGPU / Metal / Vulkan）、OpenCL、CPU SIMD、Halide |
| カラーマネジメント | Little CMS、OS の色管理 API、OpenColorIO |
| レンズ補正 | lensfun、DCP / LCP プロファイル |
| メタデータ | Exiv2、ExifTool、軽量ライブラリ + XMP 自前実装 |
| カタログ DB | SQLite（FTS5 / JSON）、DuckDB、組み込み KV |
| サムネイル / プレビュー | libvips、埋め込み JPEG 利用、独自キャッシュ形式 |
| 画像入出力 | libjpeg-turbo、libtiff、libheif、libavif、libjxl |
| ML 推論（将来） | ONNX Runtime、Core ML、DirectML |

## 評価方法
- 評価軸: 性能 / 開発効率（開発者のスキル前提で）/ クロスプラットフォーム / 成熟度・保守状況 /
  ライセンス適合性（前提のライセンス方針に照らして）/ 配布の容易さ / 学習コスト
- 各候補を 1〜5 で採点し、評価軸の重みを明示した加重スコア表を作成してください。
- 重みを変えると結論が入れ替わる箇所（感度の高い論点）を指摘してください。
- レイヤー間の相性（例: UI とパイプラインの間で大きな画像バッファをどう受け渡すか）を考慮し、
  単体の最適ではなく「組み合わせ」として 2〜3 案の技術スタックを提示してください。

## 注意
- ライセンス（GPL / LGPL / 独自ライセンス）は前提のライセンス方針と照合し、
  影響がある場合は明示してください。記載は「要公式確認」として扱ってください。
- 保守が停滞している可能性があるライブラリは、その旨と確認方法を書いてください。
- 確信度が低い情報には「不確実」と明記してください。推測で断定しないでください。

## 出力
- レイヤー別比較表（候補 / 各評価軸スコア / 加重合計 / ライセンス / 主なリスク）
- 推奨技術スタック案 2〜3 個（構成図をテキストまたは Mermaid で、長所・短所・向いている条件）
- 最終推奨とその理由
- 決定前に PoC で確かめるべき事項のリスト（何を・どう測り・何を合格基準にするか）
```

## [4] アーキテクチャ設計

```
{{前提条件シート}}

## これまでの決定事項
{{[1]〜[3] の成果物と採用した技術スタック}}

## 依頼
採用した技術スタックで、MVP〜v1 を見据えたアーキテクチャを設計してください。

1. 全体構成
   - プロセス / スレッド構成（UI、現像エンジン、バックグラウンドジョブ、DB アクセス）
   - モジュール分割と依存方向（Mermaid のコンポーネント図）

   - 現像パラメータのスキーマとバージョニング（処理バージョンの扱い）
3. カタログ
   - ER 図（写真、フォルダ、ボリューム、キーワード、コレクション、スマートコレクション、
     現像設定、履歴、スナップショット、仮想コピー、スタック、プレビューキャッシュ）
   - 主要クエリとインデックス設計
   - ファイル移動・リネーム・外付けドライブ切断時の扱い
   - XMP サイドカーとの同期方針（どちらを正とするか、競合時の扱い）
4. プレビュー / サムネイルキャッシュ
   - 解像度階層、保存形式、容量管理、無効化のタイミング
5. 並行処理とエラー処理
   - ジョブキュー、キャンセル、優先度（表示中の写真を優先 など）
   - 破損ファイルや未対応機種への対応
6. 拡張性
   - 新しい補正ツールの追加方法（ツールのプラグイン化インターフェース案）
   - 将来の AI 機能（マスク、ノイズ除去）を差し込む位置

## 出力
- アーキテクチャ設計書（Markdown、図は Mermaid）
- 主要なデータ構造 / インターフェースの定義例（採用言語で）
- 設計上のトレードオフと、採用しなかった代替案
- 未決事項・リスク一覧
```

## AI に依頼するときの共通のコツ

- 一度に全部を依頼せず、フェーズごとに出力をレビューしてから次へ進める
- 「不確実な点は不確実と書く」「推測で断定しない」「仮定を明記する」を毎回指示に含める
- 数値（性能・対応機種数・価格）やライセンスは、AI の回答をそのまま採用せず一次情報で確認する
- 結論に不満があれば「前提条件のうち ◯◯ を △△ に変えた場合、結論はどう変わるか」と聞く
