## 1. 目的と合格基準（05 からの引用）

| 項目 | 内容 |
|---|---|
| 目的 | LibRaw で手持ちの ARW をすべて正しく展開できるかと、ワーカープロセスでの隔離の方式を確認する（AR-7, AR-10） |
| 検証内容 | Rust から LibRaw を FFI で呼び出し、Windows と macOS でビルドする。RAW データ・黒レベル・白レベル・カメラ行列・撮影時の WB・埋め込み JPEG・撮影情報を取得する。**LibRaw の各行列（`cam_xyz`、`rgb_cam` など）の意味と基準の光源を、実際の API とデータで確認する**（04 の 2.6 節）。展開を **ワーカープロセス** で行い、共有メモリで本体に渡す最小の仕組みを作る（04 の 1.2 節） |

| 測定方法 | 展開の成否と、1 枚あたりの展開時間を計測する。CFA の実際のバッファのサイズ（余白を含む）を記録する。複数スレッドで並行して展開できるかを確認する。**壊れたファイル**（途中で切れたもの、メタデータは読めるが画像データが壊れたもの、寸法が異常なもの、処理が終わらないもの）を入力して、ワーカーの異常終了・タイムアウト・再起動・再試行の上限が設計どおりに動くかを確認する |

| 想定工数 | 1.5〜2 週（M0 の中で PoC-1 と並行して進める） |

## 3. この環境で AI が確認した事項（参考: 実機ではない）

この環境の構成は [README](README.md) の 5 章です。**判定には使いません。** 実際の ARW（2 枚）での参考の確認は 3.1 節です。それ以外の項目は合成データでの確認です。

- **合成 DNG の展開**（LibRaw 0.21.2、`crates/genzo-raw/tests/libraw.rs`）: 4 種類の CFA の並び、メタデータの往復、すべての向き、余白（偶数・奇数）、D65 の行列の選択、埋め込みサムネイル、ファイルとメモリ上のデータの API の一致、ASCII 以外の文字を含むパスと読み取り専用のファイル、複数スレッドでの並行展開の結果の一致。macOS の CI の設定では、Homebrew の LibRaw を入れて同じテストを実行します（CI の実行結果はこのページでは確認していません）。
- **ワーカーの隔離**（`crates/genzo-worker/tests/`）: 異常終了からの回復と次のジョブの成功、孫プロセスがパイプを持ったままの異常終了の検出、ハングのタイムアウトと再起動、不正な出力（プロトコルのエラー）、偽ったバッファの検証による拒否、同じファイルで 2 回続けて失敗したらスキップ、取り消しによる強制終了と再起動、共有メモリが足りない場合の確保し直し、途中で切れた DNG で本体が落ちないこと（機能フラグ `libraw`）、Linux の `RLIMIT_DATA` によるメモリの上限。
- **本体の実行ファイルと LibRaw**: Linux（Ubuntu 24.04）で `--features genzo-cli/libraw` でビルドした `genzo` と `genzo-worker` が `libraw_r.so` に依存しないことを `ldd` で確認（2026-10-10。[第三者の台帳](../third_party.md) の 3.1 節）。その時点では、どちらも LibRaw の関数を呼んでいませんでした。第 3 波（`genzo-cli` がワーカーを兼ねる構成）の後は、`genzo` が `libraw_r.so.23` に依存することを `ldd` で確認（2026-10-10）。決定事項ログ No.32（配布するアプリはワーカーを別の実行ファイルにする）の後、別々の cargo の実行でビルドすると、`genzo-worker`（libraw あり）は `libraw_r.so.23` に依存し、`genzo`（なし）は依存しないことを `ldd` で確認（2026-10-10、実装の報告による）。
- **孫プロセスをまとめて終わらせる仕組み**（2026-10-10。決定事項ログ No.39）: Linux の結合テスト（`crates/genzo-worker/tests/process.rs` の `grandchildren` の 5 件。ffmpeg を模した子プロセスで、強制終了・タイムアウト・異常終了・終了の依頼と drop・本体の入力が閉じた場合）。修正の前は 5 件とも「20 秒たっても孫プロセスが残っている」で失敗した。
- **未確認**: 実機の ARW の記録方式のうち非圧縮・ロスレス圧縮（3.1 節）、Windows でのビルドと動作（ジョブオブジェクト・メモリの上限を含む）、macOS での本体のリンクとプロセスグループ。

- ワーカー経由の費用は、同じプロセスでの展開との差から約 17 ms / 35 ms と推定（推測: 差し引きによる）。

**並行展開**: 2 ワーカーでは処理量が約 1.65 倍になった。12 回すべての結果が、1 つずつの展開と一致した（CFA のハッシュで比較）。同じプロセスの 2 スレッドでも一致した。

**LibRaw の行列**（04 の 2.6 節）
- `cam_xyz`: LibRaw の表（adobe_coeff）÷ 10000 と完全に一致した。
- `rgb_cam`: 行ごとに正規化した `cam_xyz` × sRGB→XYZ の逆行列。再計算との差は 4.8e-7 以下。
- genzo の「カメラ（WB 後）→ BT.2020」: (sRGB→BT.2020) × `rgb_cam` と 1.1e-4 以内で一致した。WB した中立色は (1, 1, 1) になる。
- 基準の光源: D65（Adobe の ColorMatrix2）と推測する。根拠は第三者の資料（RawTherapee の camconst.json）の注記と、値の一致。**Adobe DNG Converter の出力とは未照合**。
- LibRaw の `WB_Coeffs[21]`（D65）は、Sony では昼白色の蛍光灯（`[13]`）と同じ値。D65 の測定値として使えない。

**壊したファイル**（元のサンプルから作った 30 件。作り方と SHA-256 は 3.1.5。`genzo info`・`genzo render` と、1 つの WorkerClient で 3 回ずつ）
- 本体は一度も落ちなかった。ワーカーの異常終了・タイムアウトもなかった。
- **途中で切れたもの（10% / 50% / 90%）6 件、データの位置がファイルの外のもの 2 件、最後の 1 KiB を削った a7c の 1 件の、計 9 件は、エラーにならずに現像された。**
  - 原因: LibRaw 0.21.2 の `sony_arw2_load_raw` が `fread` の戻り値を見ていない。
  - 結果: 読めなかった行は直前の行の繰り返しになる。データがない場合は、初期化していないメモリが画素になる。
- 最後の 1 KiB を削った a7iv は、RAW のデータの後ろの詰め物（2,560 B）の一部を削っただけで、展開の結果は元とバイト単位で同じ（正しい動作）。
- 画像データを乱数・0・0xFF で上書きしたものは、壊れた画素のまま現像された（圧縮した ARW にはチェックサムがなく、検出できないのは想定どおり）。
- 寸法を異常にしたもの・ヘッダを壊したもの・ARW でないものは、`Unsupported` か `Decode` のエラーになった。
- ハング・異常終了（ワーカーのテスト用の口。実際の `genzo __worker`）: ハングはタイムアウトを 2 s にして約 2011 ms でタイムアウトし、再起動した。同じファイルで 2 回続けて失敗すると、3 回目はスキップされた。異常終了は 5 ms で検出して再起動した。

**メモリの上限（Linux の RLIMIT_DATA）**
- 64 MiB: a7c-cmp-01 でワーカーが SIGABRT になった（Rust の確保の失敗）。本体は異常終了として扱い、再起動した。
- 96 MiB 以上: 2 ファイルとも成功した。
- ワーカーの VmHWM は約 96〜104 MB だった。

**本体が異常終了した後の共有メモリ**: 終了したプロセスの一時ディレクトリが残っていた（この計測で作ったものではない）。計測したコミットでは、掃除の関数 `purge_stale_arenas` はアプリから呼ばれていなかった（修正の後の確認は 3.1.2 の A-5）。

**見つかった不具合**（修正は 3.1.2）
1. 途中で切れた ARW がエラーにならない。
2. α7 IV の APS-C の詰め物の列と異常な行が出力に出る。
3. 飽和の判定が白レベルの 16380 で、実際に緑が張り付く値 16372 と合わない（16372 以上の G 2,132 画素のうち、`DN ≥ 白レベル` で飽和と判定されるのは 207 画素（約 9.7%）だけ）。
4. メモリの上限に当たると、ワーカーが SIGABRT で終わる。
5. 残った共有メモリを掃除する処理が呼ばれていない。
6. `crates/genzo-raw/src/decode.rs` の doc の「ファイルの終わりを超える読み込みは LibRaw が中断する」が、`sony_arw2_load_raw` には当てはまらない。

#### 3.1.2 修正の後の挙動（2026-10-10。決定事項ログ No.59）

各不具合は、修正を外すと失敗するテストを先に書いてから直した（実装の報告による）。

- **A-1 途中で切れた ARW**: 展開の関数が `sony_arw2_load_raw()` のとき、展開の前に「データの位置 ＋ データの大きさ ＞ 入力の大きさ」を確かめ、超えていれば `RawError::Decode` にする（メモリから開く場合も同じ値で確かめる）。タイルのある形式では LibRaw の値の意味が違うため、ほかの展開の関数では確かめない（ロスレス圧縮などでの確認は残る。[implementation_status](../implementation_status.md) の表 No.57）。
  - 実機のサンプルの回帰テスト（3.1.3）で、2 枚それぞれについて、10% / 50% / 90% で切ったもの・データの位置をファイルの外にしたもの・データの終わりより前で切れる「最後の 1 KiB を削ったもの」（a7c）がエラーになり、データの後ろの詰め物だけを削った a7iv の「最後の 1 KiB を削ったもの」が元と同じ CFA になることを確かめた（パスから開く場合とメモリから開く場合の両方）。データの終わりは a7c-cmp-01 が 24,955,648 B（ファイルの大きさと同じ）、a7iv-apsc-cmp-01 が 17,643,008 B（後ろに 2,560 B の詰め物）。
  - `genzo render` で途中で切ったファイル 5 件を現像し、終了コード 1 になった（実装の報告による。内訳は報告に記載がなく**要確認**）。
- **A-2 既定の切り抜き**: `raw_inset_crops[0]` を `RawImage::default_crop` として持ち（ワーカーのプロトコルの版 2）、デモザイクは有効画素の全体で行い、G の基準の枠・ガイド・利用者の切り抜き・元の寸法を既定の切り抜きの範囲にした（04 の 2.7 節。GPU 版も同じ値）。
  - 実機の 2 枚を `genzo render`（release、`--features libraw`）で現像すると、出力は 6000 × 4000（a7c-cmp-01）と 3072 × 4608（a7iv-apsc-cmp-01。向き 8）で、端の帯・線は指標でも目視でもなかった。GPU 版（llvmpipe）と CPU 版の差は 8bit 換算で最大 0.0039。
  - 既定の切り抜きを外して現像すると、a7iv-apsc-cmp-01 で上端の平らさの比が 0.012、右端の色の段差の比が 2.85 になり、筋と線を検出できた（回帰テストの判定の閾値 0.25・2.0 は、この計測をもとにした仮置き）。
- **A-3 飽和の閾値**: 白レベルと分け、仮置きの式「黒 ＋（白 − 黒）× 0.995」にした（a7c-cmp-01 は 16303.65、a7iv-apsc-cmp-01 は 16300.66）。CPU 版と GPU の Draft の両方で使う。a7iv-apsc-cmp-01 の張り付いた緑 2,132 画素は、すべて飽和の印が付いた。0.995 は a7iv-apsc-cmp-01 の 1 枚だけが根拠（a7c-cmp-01 は最大 7740 で飽和していない）。
- **A-4 確保の失敗**: CFA とサムネイルの確保を `try_reserve_exact` にし、失敗を `RawError::Decode` にした（`genzo-worker` のテストで、64 MiB 以上のメモリの上限で展開が通常のエラーになることを確認。Linux・LibRaw のとき。修正の前は SIGABRT）。
- **A-5 共有メモリの掃除**: 全体レビューの指摘 F22 の修正で、一時ディレクトリを作る前に `purge_stale_arenas` を呼ぶ（持ち主のロックファイルで判定）ようになっていることを確認した（変更なし）。
- **A-6・A-7**: `RawError::Decode` の表示を「RAW のデータを読み取れません」にした。`RawDetails` に、既定の切り抜き・使わなかった理由・SonyRawFileType・データの位置と大きさ・入力の大きさ・確認したか・飽和の閾値を加えた（`genzo info --json` への出力はまだ）。
- **ワーカーのメモリの上限と孫プロセス**（決定事項ログ No.39）: 上限の既定は 2 GiB（仮置き。上の VmHWM 約 96〜104 MB に、α7 IV のフルサイズと並行の余裕を見込んだ）。孫プロセスはまとめて終わらせる（3 章の箇条書き）。
