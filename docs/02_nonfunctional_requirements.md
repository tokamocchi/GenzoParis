# [2] 非機能要件の定義

- 入力: `prompts/premise_sheet.md`（前提条件シート）、`docs/01_feature_inventory.md`（[1] の成果物）
- 位置づけ: たたき台。目標値はすべて **PoC（[5]）で実測して見直す前提** です。
- 根拠の強さ
  - **一般原則**: 広く知られた UX の目安や技術的な原理に基づく
  - **試算**: この文書内の計算に基づく（計算過程は付録 A）
  - **要実測**: 経験的な仮置きの値。PoC で妥当性を確認する

---

## 0. 基準とする環境と前提データ

| 項目 | 内容 |
|---|---|
| 基準カメラ | α7 IV：7008 × 4672 ≒ 3,274 万画素（性能の上限ケース）／ α7C：6000 × 4000 = 2,400 万画素 ※画素数は公式仕様で要確認 |
| 基準動画 | DJI Osmo Pocket の MP4 / MOV。最も重いケースとして 4K・H.265・10bit を想定する（機種と設定は要確認） |
| 実機（性能測定に使う PC） | **Windows 11**：メモリ 32GB、NVIDIA GeForce RTX 3080（VRAM 10GB / 12GB のどちらかは要確認）、内蔵 SSD ／ **macOS**：M1 搭載 Mac（2021 年頃に購入。メモリ容量は要確認）、内蔵 SSD |
| 性能目標の基準機 | 2 台のうち性能が低い **M1 Mac** を基準機とし、性能目標は M1 Mac で満たすことを条件にする。Windows 機（RTX 3080）は余裕があるはずなので、両方で計測して差を確認する |
| カタログ規模 | 写真と動画を合わせて最大 50 万件 |
| 保存場所 | カタログ・プレビューキャッシュ・写真本体とも内蔵 SSD |

性能の目標値は、特に断りがない限り **M1 Mac × α7 IV の ARW × 50 万件のカタログ** で測ります。

UX の目安としては、次の応答時間の 3 段階（Jakob Nielsen による整理）を使います。
- 0.1 秒以内: 操作に直接反応していると感じる
- 1 秒以内: 待たされていると感じるが、思考は途切れない
- 10 秒以内: 注意を保てる限界（これを超える処理には進捗表示が必要）

## 1. 非機能要件一覧

### 1.1 性能（PERF）

| ID | 要件 | 目標値 | 根拠 | 検証方法 |
|---|---|---|---|---|
| PERF-01 | 現像スライダーの追従性 | ドラッグ中、画面に収まるサイズのプレビューを **30fps 以上（1 フレーム 33ms 以内）** で更新する | 一般原則（0.1 秒以内なら直接操作と感じる。滑らかに見えるには 30fps 程度が必要）。重視点 2 | 露光量・トーンカーブ・ハイライト / シャドウの各スライダーを自動操作し、フレーム時間を計測する |
| PERF-02 | スライダーを離した後の最終描画 | 画面表示に使う解像度での高品質な描画を **0.5 秒以内** に完了する | 一般原則（1 秒以内）。要実測 | 同上。最後の操作から描画完了までの時間を計測する |
| PERF-03 | 等倍表示 | 100% 表示に切り替えてから、表示範囲の描画が完了するまで **1 秒以内** | 一般原則。要実測 | 等倍表示へ切り替えて計測する |
| PERF-04 | ルーペでの写真送り（キャッシュあり） | 次の写真の表示まで **0.1 秒以内** | 一般原則。選別の効率に直結する | 100 枚を連続で送り、各回の表示時間を計測する |
| PERF-05 | ルーペでの写真送り（キャッシュなし） | 埋め込み JPEG を **0.2 秒以内** に表示し、その後で現像結果に差し替える | 要実測 | キャッシュを消した状態で計測する |
| PERF-06 | グリッドのスクロール | **60fps** を維持する。キャッシュ済みのサムネイルは表示範囲に入ってから **0.1 秒以内** に表示する | 一般原則 | 50 万件のカタログで高速スクロールし、フレーム落ちを計測する |
| PERF-07 | フィルター・並べ替えの応答 | 50 万件に対して **0.2 秒以内**（最初の表示まで） | 一般原則（0.1〜1 秒）。要実測 | 代表的なフィルターの組み合わせ 10 種で計測する |
| PERF-08 | フォルダの登録 | 写真 1,000 枚の登録（メタデータ読み込みと埋め込みサムネイル抽出）を **30 秒以内** に完了する。登録の途中からサムネイルを順次表示する | 要実測 | 1,000 枚のテストフォルダで計測する |
| PERF-09 | 現像プレビューの生成（バックグラウンド） | 1 枚あたり **1 秒以内**（推奨構成。複数枚を並列処理する） | 要実測 | 1,000 枚を一括生成して平均を計測する |
| PERF-10 | 書き出し | α7 IV の写真をフル解像度の JPEG で 1 枚あたり **3 秒以内** | 要実測 | 100 枚を書き出して平均を計測する |
| PERF-11 | 動画サムネイルの生成 | 4K / H.265 / 10bit の動画 1 本あたり **2 秒以内** | 要実測 | 代表的な動画 20 本で計測する |
| PERF-12 | アプリの起動 | 50 万件のカタログで、グリッドが操作可能になるまで **3 秒以内** | 要実測 | 起動時間を計測する |
| PERF-13 | 操作の非ブロッキング | 重い処理（登録・プレビュー生成・書き出し）の実行中も、UI 操作への応答が 0.1 秒を超えて止まらない | 一般原則 | 一括書き出し中に UI 操作の応答時間を計測する |

### 1.2 リソース・スケーラビリティ（SCL）

| ID | 要件 | 目標値 | 根拠 | 検証方法 |
|---|---|---|---|---|
| SCL-01 | カタログの規模 | 50 万件で、PERF の目標をすべて満たす | 前提条件 | ダミーデータで 50 万件のカタログを作って計測する |
| SCL-02 | カタログ DB のサイズ | 50 万件で **5GB 以下** | 要実測 | ダミーデータで計測する |
| SCL-03 | サムネイルキャッシュ | 全件を保持する。50 万件で **10〜15GB** 程度に収める（1 件あたり 20〜30KB） | 試算（付録 A-2） | 実際の写真でサムネイルの平均サイズを計測する |
| SCL-04 | 現像プレビューキャッシュ | **全件は保持しない**。上限容量（既定値は 50GB 程度）を設け、最近使ったものを優先して残す | 試算：1 件 500〜800KB × 50 万件 = 250〜400GB となり、内蔵 SSD には置けない（付録 A-2） | 上限を超えたときに古いものから削除されることを確認する |
| SCL-05 | メモリ使用量 | 推奨構成（16GB）で、通常操作時に **4GB 以下**。一括処理時も **8GB 以下** | 試算：α7 IV のフル解像度画像は、作業用のバッファ 1 枚で 262〜524MB になる（付録 A-1）。フル解像度のバッファを同時に何枚も持たない設計が必要 | 長時間の連続操作でメモリ使用量を監視する |
| SCL-06 | GPU メモリ | M1 の統合メモリ（CPU と GPU で共有）でも動作する。フル解像度の処理はタイル単位で行う | 試算（付録 A-1）。M1 Mac のメモリ容量によっては余裕が小さいため | M1 Mac で動作を確認する |
| SCL-07 | 処理の並列度 | CPU のコア数に応じてバックグラウンド処理を並列化する。UI 用に一定の余力を残す | 一般原則 | コア数の異なる PC で PERF-09 を計測する |

### 1.3 画質・色（IQ）

| ID | 要件 | 目標値 | 根拠 | 検証方法 |
|---|---|---|---|---|
| IQ-01 | 作業色空間とビット深度 | 現像処理は **シーンリニアな広色域の色空間**（例：リニア Rec.2020 / ProPhoto RGB）で行う。中間データは **浮動小数点**（書き出しには 32bit、プレビューには 16bit を使うかは要検討）で扱う | 一般原則（量子化による階調飛びと、途中のクリッピングを防ぐ）。重視点 1 | 強いトーン補正をかけた画像でバンディングが出ないことを確認する |
| IQ-02 | 途中でクリッピングしない | 出力変換の直前まで、0〜1 の範囲外の値を保持する | 一般原則（露光を下げたときにハイライトを復元できる） | 露光量 +3EV の後に −3EV をかけた結果が元に戻ることを確認する |
| IQ-03 | デモザイクの品質 | 偽色・迷路状のアーティファクト・ジッパーノイズが目立たない。高品質モードを既定にする | 重視点 1 | 解像度チャートと、細かい模様のある実写で、基準となる現像結果と目視で比較する |
| IQ-04 | 色再現の妥当性 | カメラの色変換の結果が、基準（カラーチャートの撮影画像の理論値）と比べて **平均 ΔE2000 が 3 以下** | 要実測（ΔE2000 が 2〜3 前後が「よく見ると差がわかる」程度とされる）。重視点 1 | カラーチェッカーを撮影した ARW を現像し、各色パッチの ΔE を計測する |
| IQ-05 | 表示の色管理 | モニタープロファイルを反映して表示する（Windows / macOS の両方）。プロファイルが取得できない場合は sRGB とみなし、その旨を表示する | 重視点 1 | 広色域モニターで、sRGB 画像と P3 画像の表示を、OS 標準の画像ビューアと比較する |
| IQ-06 | 書き出しの色の正確さ | 書き出し時に ICC プロファイルを埋め込む。アプリ上の表示と、書き出したファイルを色管理対応ビューアで開いた表示が一致する | 一般原則 | 書き出したファイルを OS 標準ビューアで開いて比較する |
| IQ-07 | プレビューと書き出しの一致 | 同じ解像度に縮小して比べたとき、GPU 版の処理結果と CPU 版（基準実装）の処理結果の差が **8bit 換算で ±1 以内**（またはピクセルごとの ΔE2000 が 1 以下） | 試算・要実測。GPU と CPU では浮動小数点演算の結果が完全には一致しないため、許容誤差を定める | 回帰テスト用の画像セットで差分を自動計算する |
| IQ-08 | 処理結果の再現性 | 同じ入力・同じパラメータ・同じ処理バージョンなら、アプリを更新しても書き出し結果が変わらない（IQ-07 の許容誤差の範囲内） | 非破壊編集の前提。重視点 1 | 回帰テスト（MAINT-03）で検証する |
| IQ-09 | 動画の表示色 | 動画サムネイルは、動画に記録された色空間（Rec.709 など）を考慮して sRGB に変換する。Log 動画の LUT 適用は later | 一般原則 | 代表的な動画で、OS 標準のプレイヤーと比較する |

### 1.4 データ保全（DATA）

| ID | 要件 | 目標値 | 根拠 | 検証方法 |
|---|---|---|---|---|
| DATA-01 | 元ファイルを書き換えない | 写真・動画の元ファイルは **読み取り専用** で開く。アプリのどの操作でも内容を変更しない（ファイル操作機能による移動・リネームを除く） | 非破壊編集の大前提 | すべてのテストの前後で、元ファイルのハッシュが変わらないことを確認する |
| DATA-02 | カタログ更新の原子性 | 更新はトランザクションで行う。処理の途中でアプリが強制終了したり電源が落ちたりしても、カタログが壊れない | 一般原則 | 書き込み中にプロセスを強制終了するテストを繰り返す |
| DATA-03 | 失われる操作の範囲 | 強制終了しても、失われるのは直前の **数秒以内** の操作だけ | 要実測 | 同上 |
| DATA-04 | 自動バックアップ | 既定では 1 日 1 回（またはアプリの終了時）にカタログをバックアップし、**7 世代** 保持する。保存先と世代数は設定で変更できる | 一般原則。世代数は仮置き | バックアップからの復元手順をテストする |
| DATA-05 | 整合性チェック | 起動時に簡易チェックを行い、手動で詳細チェックを実行できる。問題が見つかった場合は、修復またはバックアップからの復元を案内する | 一般原則 | 意図的に壊したカタログで動作を確認する |
| DATA-06 | 削除の安全性 | 写真の削除は OS のゴミ箱を経由する。直接は消さない | 一般原則 | 削除後にゴミ箱から復元できることを確認する |
| DATA-07 | ファイル操作の安全性 | 移動・リネームは、実ファイルの操作とカタログの更新が食い違わない手順で行う（失敗時はロールバックする） | 一般原則 | 操作の途中で失敗させるテストを行う |
| DATA-08 | カタログのマイグレーション | アプリの更新でカタログのスキーマが変わるときは、事前に自動でバックアップしてから移行する | 一般原則 | 旧バージョンのカタログから移行するテストを行う |
| DATA-09 | 現像パラメータの処理バージョン | 現像設定は処理バージョンとともに保存する。新しいアルゴリズムは明示的に移行した写真にだけ適用する | IQ-08 を実現するため | 旧バージョンの設定で現像した結果が変わらないことを確認する |

### 1.5 互換性・移行性（COMPAT）

| ID | 要件 | 目標値 | 根拠 | 検証方法 |
|---|---|---|---|---|
| COMPAT-01 | 対応する RAW | α7 IV / α7C の ARW のうち、カメラで選べるすべての記録方式（非圧縮・圧縮・ロスレス圧縮など。機種ごとの対応方式は要確認） | 前提条件 | 各記録方式で撮影したサンプルで確認する |
| COMPAT-02 | 対応する動画 | DJI Osmo Pocket の MP4 / MOV（H.264 / H.265、8bit / 10bit） | 前提条件 | 各設定で撮影したサンプルで確認する |
| COMPAT-03 | その他の画像 | JPEG / TIFF / PNG / HEIC を登録・閲覧できる（HEIC の扱いは未決） | 一般的な利用 | サンプルで確認する |
| COMPAT-04 | データの持ち出し | カタログのスキーマを文書化する。評価・キーワードは、標準的な形式（CSV や XMP）で書き出せる（v1 以降） | ツールに依存しないため（ORG-07） | 書き出したデータを他のツールで読めることを確認する |
| COMPAT-05 | Lightroom 互換 | 求めない | 前提条件 | — |

### 1.6 保守性・テスト容易性（MAINT）

AI が主に実装・保守する前提なので、この分類を特に重視します。

| ID | 要件 | 目標値 | 根拠 | 検証方法 |
|---|---|---|---|---|
| MAINT-01 | 処理部と UI の分離 | 現像エンジンとカタログ処理を、UI なしで動かせる（ライブラリと CLI として） | 自動テストと AI による検証のため | CLI だけで登録・現像・書き出しができることを確認する |
| MAINT-02 | CPU による基準実装 | すべての現像処理に CPU 版の実装を用意し、これを正とする。GPU 版は CPU 版との一致をテストする | GPU のない CI 環境でもテストできるようにするため。IQ-07 | CI で CPU 版のテストを実行する |
| MAINT-03 | 画像処理の回帰テスト | 基準画像のセット（α7 IV / α7C の ARW と代表的なパラメータの組み合わせ）を用意する。コードを変更するたびに、書き出し結果が基準から許容誤差を超えて変わっていないかを自動で検証する | IQ-08。AI による変更が意図しない画質の変化を起こしていないかを検出するため | CI に組み込む |
| MAINT-04 | 静的な検査 | 型検査・リンター・フォーマッターを CI で実行し、警告ゼロを維持する | AI の誤りを早期に検出するため | CI に組み込む |
| MAINT-05 | テストのカバレッジ | カタログ処理と現像パラメータの処理は、単体テストの行カバレッジ **80% 以上** | 仮置きの値 | CI でカバレッジを計測する |
| MAINT-06 | 両 OS での CI | Windows と macOS の両方でビルドとテストを実行する | 前提条件（対象 OS が 2 つ） | CI に組み込む |
| MAINT-07 | 性能の回帰テスト | PERF の主要な項目をベンチマークとして自動実行し、悪化を検出する | 重視点 2 | CI（またはリリース前の手動実行）で計測する |
| MAINT-08 | 現像処理の追加しやすさ | 新しい補正処理を、決まったインターフェースに沿って追加できる（パイプラインの各段がプラグインのような構造） | 段階的に機能を増やすため | 新しい補正処理を 1 つ追加するのに必要な変更箇所を確認する |
| MAINT-09 | 設計の文書化 | 設計の判断と理由を記録する（決定事項ログ・アーキテクチャ設計書） | AI が文脈を把握して保守できるようにするため | レビューで確認する |

### 1.7 セキュリティ・プライバシー（SEC）

| ID | 要件 | 目標値 | 根拠 | 検証方法 |
|---|---|---|---|---|
| SEC-01 | オフライン動作 | すべての機能がネットワーク接続なしで動作する | 写真は個人情報を含みうるため | ネットワークを切断した状態でテストする |
| SEC-02 | 外部送信をしない | 利用状況の送信（テレメトリー）やクラッシュレポートの自動送信は行わない。更新の確認など通信が必要な機能は、利用者が明示的に有効にした場合だけ動作する | 同上 | 通信を監視して確認する |
| SEC-03 | 書き出し時の位置情報 | 書き出しで GPS 情報を削除する設定を用意する | プライバシー保護 | 書き出したファイルのメタデータを確認する |
| SEC-04 | 依存ライブラリの管理 | 依存ライブラリのライセンスと既知の脆弱性を CI で確認する | OSS として公開するため | CI に組み込む |
| SEC-05 | 不正なファイルへの耐性 | 壊れたファイルや不正なファイルを読み込んでも、アプリ全体が落ちたりカタログが壊れたりしない（そのファイルだけをエラーにする） | RAW / 動画のデコーダは C / C++ 製が多く、不正な入力による不具合の影響を受けやすいため | 壊れたファイルでのテストと、ファジング（v1 以降） |

### 1.9 配布・動作環境（DIST）

| ID | 要件 | 目標値 | 根拠 | 検証方法 |
|---|---|---|---|---|
| DIST-01 | 対応 OS | Windows 11 と、macOS（Apple Silicon）の現行版および 1 つ前の版。Intel Mac と Windows 10 は対象外 | 前提条件（ユーザー回答） | 各 OS で動作を確認する |
| DIST-02 | インストール | Windows はインストーラー、macOS はディスクイメージで配布する。管理者権限なしでインストールできることが望ましい | 前提条件（限られたメンバーへの配布） | 配布物でインストールテストを行う |

## 2. 技術選定に強く影響する要件トップ 5

| 順位 | 要件 | 技術選定への影響 |
|:-:|---|---|
| 1 | **PERF-01 / IQ-01 / IQ-07**：33MP の RAW でスライダーに 30fps で追従しつつ、浮動小数点で処理する。プレビューと書き出しの結果は一致させる | GPU で現像処理を行うことがほぼ必須になる。そのうえで、CPU の基準実装（MAINT-02）と同じ結果を出せる仕組み（同じアルゴリズムを両方で書く、または両方に対応した記述方式）を選ぶ必要がある。パイプラインの実行基盤とコア言語の選定に直結する |
| 2 | **IQ-05**：Windows と macOS の両方で、モニタープロファイルを反映した表示 | UI の土台の選定に直結する。Web 系の UI（WebView）では、色管理が OS とブラウザエンジンに依存し、細かく制御できない可能性がある。GPU で描画した画像を色管理したうえで UI に表示する方法を PoC で確認する必要がある |
| 3 | **SCL-01 / PERF-06 / PERF-07 / SCL-04**：50 万件での閲覧・検索性能と、キャッシュ容量の管理 | カタログ DB の選定（全文検索とインデックス）、サムネイルキャッシュの形式、仮想スクロールが得意な UI の土台の選定に影響する |
| 4 | **COMPAT-02 / PERF-11**：H.265 / 10bit の動画を両 OS で扱う | FFmpeg を同梱するか、OS の動画機能（macOS の AVFoundation、Windows の Media Foundation）を使うかの選択になる。Windows では HEVC のデコードが OS の追加コンポーネントに依存する場合がある。FFmpeg を同梱する場合は、LGPL / GPL のビルド構成とコーデックの特許の扱いを確認する必要がある |
| 5 | **MAINT-01〜04 / MAINT-06**：AI による保守を前提にしたテスト容易性 | 型の強い言語、UI から独立して動かせるコア、GPU のない CI でも動く CPU 基準実装、Windows / macOS の CI という条件が言語と構成の選定に効く。ライセンス（GPL 可）は候補を狭めないが、アプリ自体のライセンスを決める必要がある |

## 付録 A. 試算

### A-1. 画像 1 枚あたりのメモリ量

| 画像 | 画素数 | RAW（16bit × 1ch） | RGBA float16（8 バイト / 画素） | RGBA float32（16 バイト / 画素） |
|---|---:|---:|---:|---:|
| α7 IV（7008 × 4672） | 32,741,376 | 約 65MB | 約 262MB | 約 524MB |
| α7C（6000 × 4000） | 24,000,000 | 48MB | 192MB | 384MB |
| 画面表示用（2560 × 1440） | 3,686,400 | — | 約 29MB | 約 59MB |

- 現像処理では中間のバッファが複数必要になるため、フル解像度のまま処理すると、1 枚で 1GB を超えることがある。
- そのため、プレビューは画面表示に使う解像度で処理し、フル解像度の処理（等倍表示・書き出し）はタイル単位で行う設計にする（SCL-05, SCL-06）。

### A-2. キャッシュ容量（50 万件）

| キャッシュ | 1 件あたり（仮定） | 50 万件の合計 |
|---|---:|---:|
| サムネイル（長辺 256〜320px 程度の JPEG） | 20〜30KB | 10〜15GB |
| 現像プレビュー（長辺 2560px の JPEG） | 500〜800KB | 250〜400GB |

- 1 件あたりのサイズは仮定です。実際の写真で計測して見直してください。
- 現像プレビューは全件を保持できないため、上限容量を設けて LRU（最近使われていないものから削除）で管理する。既定の上限を 50GB とした場合、800KB / 件で約 62,500 件を保持できる。
