## 1. 結論

**基盤整備とリスクを確かめる PoC は進めてよい。ただし、現像エンジンとデータ操作の本実装に入る前に、色処理の契約、解像度間の一致条件、ファイル操作の復旧手順を確定する必要がある。**

Rust コアを UI から独立させる方針、CPU 基準実装、SQLite、原本を変更しない非破壊編集、UI を PoC 後に決定する進め方は妥当。問題は、未検証の成立条件が「保証される」と記述されている点と、実装に必要な境界条件が不足している点に集中している。

| 重大度 | 件数 | 判定基準 |
|---|---:|---|
| 致命的 | 0 | 文書だけで、必ずデータ消失する等の致命的欠陥を確定できるもの |
| 重要 | 17 | 画質・データ保全・主要性能・配布・見積もりに影響し、本実装前の設計修正または PoC の判定が必要 |
| 軽微 | 2 | 仕様の表現・参照・運用条件の整理が必要 |

致命的 0 件は安全性の保証ではない。特に R-06 と R-07 は、未定義のまま実装すると原本や保存済み操作の喪失につながりうる。

### 優先して解決する事項

1. **色空間・伝達関数・白色点・色域圧縮を明文化する**（R-01）。
2. **CPU/GPU の一致と、プレビュー/フル解像度の一致を別々に検証する**（R-02、R-03）。
3. **削除・書き出し・カタログ保存の安全条件を決める**（R-06、R-07）。
4. **デコードの隔離と、プロセスをまたぐ GPU の制御を具体化する**（R-05、R-10）。
5. **MVP の定義と PoC の工数・合格基準を合わせる**（R-13〜R-17）。

## 3. 指摘の詳細

### R-01：色空間と伝達関数の境界を厳密に定義する

**根拠:** [04 アーキテクチャ](04_architecture.md) 2.1 節では、ステージ 15〜16 を「Rec.2020 の色域、ガンマ約 2.2 相当」とする一方、5 章では「作業色空間 → モニター」の LUT をその値に適用する。4 章のキャッシュは Display P3。入力がリニア Rec.2020 なのか、符号化済み Rec.2020 なのか、キャッシュの P3 なのかで LUT は異なる。[02 非機能要件](02_nonfunctional_requirements.md) IQ-02 は出力直前まで範囲外の値を保持するとするが、04 のステージ 15〜16 は 0〜1 とされる。

**影響:** 実装者の解釈により二重ガンマ、誤ったプロファイル変換、色相ずれ、早すぎる色域クリッピングが起こりうる。トーンマッピングによる意図的な圧縮と、単純な clamp の区別も必要。

**改善案:**

- 各境界に、原色、白色点、伝達関数の式、線形/非線形、値域、アルファの意味を定義する。「約 2.2」で処理仕様を固定しない。
- シーンのトーン圧縮、色域圧縮、表示用の符号化を分離する。負値・高彩度・1 超の値をどの段階でどう扱うかを書く。
- リニア作業画像、Display P3 キャッシュ、sRGB 等の既存画像に、それぞれ正しい入力プロファイルからの変換を作る。
- LibRaw のどの行列を使い、WB の正規化・XYZ・色順応・作業色空間への変換をどう組み合わせるか定義する。LibRaw の `cam_xyz` と `rgb_cam` 等は同じ意味ではないため、実際の API と対象機種で確認する。参照: [LibRaw データ構造](https://www.libraw.org/docs/API-datastruct.html)。

**確認方法:** 無彩色ランプ、既知の sRGB/P3 パッチ、負値・高輝度・高彩度の人工入力を使い、CPU 変換、GPU LUT、キャッシュ表示、ICC 付き書き出しを段階ごとに照合する。IQ-02 の可逆性テストは、意図的な非線形トーン処理より前の露光処理単体で行う。

### R-02：解像度間の一致を「構造的な保証」としない

**根拠:** 04 の 2.2 節は段階 A の後でプレビューを縮小し、段階 C を実行する。書き出しはフル解像度で A〜C を実行する。2.4 節は「どちらも GPU 版なので一致は構造的に保証」としている。一般に、非線形処理と縮小の順序は交換できない。ガイドの共有や同じ WGSL の使用だけではこの差は消えない。

**影響:** トーンカーブ・彩度・デモザイク・局所補正・再サンプリングによって、縮小プレビューと書き出しの見た目が変わりうる。品質 85 程度の JPEG キャッシュも、±1 の厳密比較用の基準には適さない。

**改善案:** IQ-07 を、(a) 同じ解像度・同じ入力での CPU/GPU 数値一致、(b) フル解像度結果を縮小した画像とプレビューの画質一致、(c) 圧縮キャッシュの許容差に分ける。比較はまず非圧縮・同じ出力色空間のバッファで行い、縮小フィルタ、位置合わせ、境界、ディザリングを固定する。

**確認方法:** 細線・色境界・細かい模様・逆光の画像と強い補正を含む設定で、(a) と (b) を独立して測定する。許容差を満たせない場合は、プレビューの処理順序または目標を見直し、差を利用者が理解できる表示品質の仕様に落とす。

### R-03：ガイドの依存関係とタイルの座標系を明文化する

**根拠:** 04 の 2.1 節ではジオメトリと露光量が局所トーンの前にある。2.2 節ではガイドの再計算は「段階 A の後、またはトーン関連パラメータ変更時」とされ、露光量や切り抜きへの依存が不明。7.1 節の `input_roi` だけでは、元画像・回転後・縮小ガイド間の座標変換、画像全体の統計依存、タイル余白を説明し切れない。

**影響:** 露光変更で古い輝度ガイドを参照する、切り抜き位置で補正が変わる、タイル境界に継ぎ目が出る可能性がある。「半径を画像サイズの割合にする」だけで一致するとは限らない。

**改善案:** 各ステージの入力・出力座標系と、ガイドを計算する色空間・露光前後・切り抜き前後を固定する。ガイドを入力に依存する DAG として定義し、依存する設定をキャッシュキーに含める。クロップで全体統計を変えるか、元画像全体を基準にするかも決める。タイル処理には halo、画像端の拡張方式、必要な全体解析を追加する。

**確認方法:** 同じ設定を全画面・等倍・タイルサイズ変更・切り抜き変更で比較する。露光だけ変更した際のガイド更新と、タイルの継ぎ目を自動検査する。

### R-04：WB のたびに RAW 展開からやり直す経路を検証する

**根拠:** 04 の 2.2 節で段階 A は RAW 展開から色変換までを含み、WB 変更時に再実行される。ドラッグ中に長辺 1280px にする案でも、圧縮 RAW の展開自体が縮小に比例して速くなるとは限らない。05 の PoC-3 は時間を測るが、WB の操作応答・最終描画の合格条件は明確でない。

**影響:** 露光量は軽快でも WB だけが大幅に遅い UI になる可能性がある。PERF-02 の 0.5 秒以内の最終描画にも関わる。

**改善案:** RAW 展開と、WB/デモザイク/色変換を分ける。デコード済み CFA を現在の写真用に保持する候補を測定する。α7 IV の有効画素だけでも u16 CFA は約 65MB であり、実際のバッファ寸法・余白・ワーカー転送を含めて保持コストを測る。近似プレビューを使うなら最終品質へ切り替える条件を書く。

**確認方法:** 冷起動・デコード済みの両条件で、WB の連続操作、指を離した後、等倍表示での変更を両 OS で測る。達成できなければ、キャッシュ境界または WB の応答目標を明示的に変更する。

### R-05：不正ファイルの隔離要件と本体でのデコードが矛盾する

**根拠:** 02 の SEC-05 は不正ファイルを開いても本体が落ちないことを要求する。04 の 1.2/1.3 節では対話的現像と RAW 展開が本体にあり、8 章は「一度開けたファイルなのでリスクは小さい」とする。メタデータや埋め込み JPEG を読めたことは、フル RAW デコードが安全に完了する保証ではない。外部でファイルが変わる場合もある。

**改善案:** RAW・JPEG/TIFF 等の未知入力の解析/デコードはワーカーで行い、検証済みのバッファを本体へ渡す設計を第一候補にする。共有メモリまたは一時ファイルを用いる場合も、寸法・長さ・型・上限を本体で検証する。本体内に残すデコード経路があるなら、SEC-05 の対象と制約を修正し、例外を明文化する。

**確認方法:** メタデータは読めるが画像データが壊れた入力、異常寸法、途中切断、ハング、ファイル差し替えを試す。タイムアウト、メモリ上限、ワーカー再起動、同一ファイルの再試行上限まで確認する。

### R-06：削除と書き出しに、原本保護と復旧の状態機械が必要

**根拠:** 01 の FILE-01 は MVP。04 の 3.3 節は移動・リネームに予定記録を使うが、ゴミ箱への移動とカタログ削除の途中障害は定義していない。asset/variant 分離に対して、仮想コピーを削除する操作が元ファイルへ及ぼす影響も未定義。EXP-01 には、出力先が原本・カタログ・別の入力と同一の場合や既存ファイルとの衝突規則がない。

**影響:** DB と実ファイルの食い違い、仮想コピーからの誤った原本削除、原本の上書き、失敗した書き出しの不完全ファイルが起こりうる。これは設計不足の指摘であり、現在の実装で発生を確認したものではない。

**改善案:**

- variant の除去、asset の登録解除、原本をゴミ箱へ移す操作を別コマンドにする。原本操作では全 variant と RAW+JPEG 等への影響を表示する。
- 「予定を永続化 → OS 操作 → 結果を記録」の状態を定義し、再起動時に実ファイルと照合する。ゴミ箱が使えないときは直接削除へ切り替えず失敗扱いにする。
- 出力先と入力をパス文字列だけでなくファイル同一性でも照合する。出力は同一ディレクトリの一時ファイルへ書き、成功後に公開する。既存出力の上書き・連番・失敗を選択可能にする。

**確認方法:** 各状態間で強制終了、容量不足、権限不足を発生させる。原本のハッシュ不変、仮想コピーだけの削除、シンボリックリンク等を通じた同一出力先、復旧後の履歴・再リンクを確認する。

### R-07：アプリ終了と電源断の保存保証を分ける

**根拠:** 02 DATA-02 は電源断でも DB が壊れないこと、DATA-03 は強制終了時の操作喪失を数秒に抑えることを要求する。04 の 3.4 節は WAL+`synchronous=NORMAL` を採り、電源断で「直前のトランザクション」が失われる可能性と説明するが、失う範囲の時間上限は定義していない。

SQLite の一次資料では、WAL+NORMAL は整合性を保つ一方、電源断・OS クラッシュ後にコミット済みの変更が戻る場合がある。アプリだけのクラッシュとは扱いが異なる。参照: [SQLite synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)。

**改善案:** DATA-03 の障害モデルをアプリ終了と OS/電源断に分ける。カタログは WAL+FULL を出発点に保存の待ち時間を測り、再生成できるサムネイルは NORMAL を候補にする。NORMAL をカタログに採る場合は、どこまで操作を失うことを許すのかと、その根拠を決定事項に残す。「壊れない」と「保存済み操作を失わない」は別の保証とする。

**確認方法:** アプリ強制終了、ディスク満杯、I/O エラー、OS/電源断相当の障害を別々に検証する。プロセスを kill するテストだけで電源断耐性を実証したと扱わない。

### R-08：再現性にはアルゴリズム以外の依存も保存する必要がある

**根拠:** 04 の 2.5 節は古い `process_version` とアルゴリズムを残せば再現できる設計。RAW デコーダ、カメラ行列、レンズ DB、ICC、LUT、既定値の変更でも同じ設定の結果は変わりうる。2.3 節は f32 と演算順序で一致を保証する方向だが、WGSL の数値規則には再結合・融合や精度の幅がある。参照: [WGSL floating point evaluation](https://www.w3.org/TR/WGSL/#floating-point-evaluation)。

**改善案:** 現像結果に影響するプロファイル/LUT/レンズデータの識別子と内容ハッシュ、必要なデコーダ設定・バージョン方針を記録する。旧 process がどの依存を使うかを処理仕様として固定する。GPU の厳密一致は断定せず、ステージごとの許容誤差、NaN/Inf/負値/ゼロ付近の扱いと実機比較で保証する。

**確認方法:** カメラ行列・依存ライブラリ・GPU バックエンドを更新した状態で、旧設定の回帰画像を比較する。RTX 3080 と M1 の GPU 比較を、定期確認に加えてリリース前の必須チェックにする。

### R-09：キャッシュキーと公開・回収の契約が不足している

**根拠:** 04 の 2.2 節は入力ハッシュ・パラメータ・処理バージョンをキーにするが、4 章のファイル名は variant と develop_hash 中心。解像度・品質・色空間・プロファイル・入力変更の識別が統一されていない。3.3 節の先頭/末尾クイックハッシュは、中間部分だけの変更を識別できない。L0 は DB BLOB だが、4 章の古いキャッシュ説明はファイルと LRU が中心。

**改善案:** 入力 revision、process、外部プロファイル、現像設定、寸法、レンダー品質、キャッシュ形式/色空間を共通キーにする。クイックハッシュは候補絞り込みに使い、再リンクの確定や厳密な入力同一性に用いる場合は全体ハッシュ等で確認する。外部更新・L0 の置換/回収・原本 JPEG の ICC/向き・DB とファイルの公開順序を定義する。

**確認方法:** 同じ設定でサイズ/色空間だけ変更、元ファイルの中間部分だけ変更、生成途中の終了、古い世代の遅延完了、仮想コピー増加を試す。古い成果物が新しい成果物を上書きしないことを確認する。

### R-10：本体とワーカーをまたぐ GPU 制御を設計する

**根拠:** 04 の 1.2 節は一括書き出しを別プロセスに置く。2.4 節は GPU 書き出しを既定とする。6.1 節は本体の GPU スレッドで優先度順に処理し、書き出しタイルの合間に P0 が割り込めるとする。独立したワーカーの GPU キューやメモリは、本体のキューだけでは制御できない。

**改善案:** GPU の投入を本体で一元管理する方式か、プロセス間の処理予算・投入数・協調キャンセルを持つ方式を選ぶ。標準入出力はジョブ制御用とし、大きな画像を渡す手段、バッファ所有権、異常終了時の回収を別途定義する。rayon/tokio/複数ワーカーの並列度は、CPU コア数だけでなくメモリ量で制限する。

**確認方法:** 複数書き出し中に現像・写真送り・キャンセルを行い、操作から表示までの遅延、両プロセスを合算したメモリ、GPU 使用量、キャンセル完了時間を測る。投入済み GPU コマンドがすぐ停止する前提を置かない。

### R-11：日本語検索は FTS5 のトークナイザーまで選ぶ

**根拠:** 04 の 3.1 節はファイル名・キャプション・キーワードを FTS5 対象にするが、日本語の部分一致や正規化を定義していない。FTS5 の既定の単語検索と任意の部分文字列検索は別機能。trigram でも 3 文字未満の全文クエリに制約がある。参照: [SQLite FTS5 tokenizers](https://www.sqlite.org/fts5.html#tokenizers)。

**改善案:** 完全一致・前方一致・部分一致の期待値を決める。日本語、全角/半角、濁点、英大小文字、記号入りファイル名を正規化するかを書く。trigram・形態素分割・短語専用検索等を比較し、利用する SQLite の実ビルドで機能と索引サイズを確認する。

**確認方法:** 「京都」「海」「夕焼け」「京都旅行」や英数字混在の実データで、検索結果の正しさと 50 万件の所要時間を測る。入力 `MATCH` 構文をそのまま実行せず、検索式のエスケープ/組み立てを検証する。

### R-12：ER 図を運用可能なカタログ仕様へ補う

**根拠:** 04 の 3 章は概念 ER と代表索引まで。主ファイルの一意性、マスター variant の一意性、同じフォルダの再登録、削除時の参照整合性、検索一覧生成後の更新が未定義。id 全件を保持する方式には、検索世代・ソートの同順位規則・変更時の再構築方針がない。起動時チェック、バックアップ、履歴の容量も PoC-6 の合格条件に十分含まれていない。

**改善案:**

- DDL に FK/UNIQUE/CHECK と削除規則を定義し、接続の FK 有効化を確認する。パスの大文字小文字・Unicode・リンクをどう扱うか決める。
- MVP の再登録は冪等にする。高度な重複検出を v1 にしても、同じ登録を繰り返して増殖する挙動は避ける。
- 検索結果に世代 ID を持たせ、日時/評価等に variant_id の tie-breaker を追加する。書き込みで結果が変わった際の再構築・選択位置・遅延応答の扱いを決める。
- 概念スキーマの全 v1 テーブルを M0 で作る必要はない。MVP 必須の制約を優先する。
- 5GB の DB と 7 世代のバックアップは上限試算で約 40GB、さらに thumbs 10〜15GB と preview 50GB で約 100〜105GB（原本・一時ファイル・WAL を除く）。空き容量と保持世代を含む予算を作る。50 万件は asset 数か variant 数か明確にする。

**確認方法:** 再登録・中断再開、検索中の評価変更/削除、同順位のソート、履歴が増えたカタログ、キャッシュの読み書き同時実行を測る。DB サイズには索引・FTS・履歴を含め、WAL の増加とバックアップ時の空き領域も別計測する。起動 3 秒と整合性チェックを同時に満たせるか確認する。

### R-13：画質と性能の検証を再現可能にする

**根拠:** 05 の PoC-4 は晴天の ColorChecker と基準値の平均 ΔE2000 を比較するが、照明・基準値の白色点・露出/WB・トーン設定・Lab 変換条件がない。PoC-1 は OS ビューアとの目視比較中心。PoC-3 は最小パイプラインの時間を「書き出し相当」とするが、02 PERF-10 は JPEG の実書き出し。PERF-01 の 33ms も GPU 計算だけでは入力から画面表示までを測れない。

**改善案:** カメラ色変換の評価と、美観のためのトーン処理を分ける。チャートの参照データ、照明、WB/露出合わせ、白色点と Lab 変換を固定する。同じチャートをプロファイル作成と評価の両方に使うなら独立した検証画像も用意する。平均だけでなく最大/分布と中性色の偏りを報告する。計算時間、デコード、転送、JPEG エンコード、ファイル書き込み、入力から表示までの時間を分ける。

**確認方法:** サンプル ID・ハッシュ、設定 JSON、OS/GPU/ライブラリ版、キャッシュの冷温条件、測定回数を結果に残す。平均と p95/最大、遅れたフレームも報告する。表示は目視に加え、既知のプロファイル変換との数値比較を行う。ΔE と RGB ±1 は等価と扱わず、どちらをどのテストに使うか固定する。

### R-14：MVP の範囲を資料間で合わせる

**根拠:** 01 PRV-04 は容量管理が v1 だが、02 SCL-04 と 04 の 4 章は上限付き LRU を必要とする。01 SYS-08 は配布物が v1 だが、05 の M5 はインストーラーを含み、前提条件もメンバーへの配布を要求する。01 EXP-04 はメタデータ制御が v1 だが、02 SEC-03 は GPS 削除設定を要求する。CLI は ORG-05 で v1 だが、M2/M3 は CLI での完了を要求する。

**改善案:** 内部必須機構と利用者向け拡張を分ける。容量上限/回収、配布に必要な最小インストーラー、GPS 削除、検証用最小 CLI は MVP に明記する。高度な書き出しプリセット、汎用スクリプト API、自動更新等は v1/later に残せる。JPEG/TIFF/PNG の対応範囲も、MVP ストーリーの JPEG だけの記述と合わせる。

**確認方法:** 各 MVP 要件をマイルストーンと受け入れシナリオへ対応させる表を作る。重複した要件や「非機能だから実装作業がない」と扱った項目を残さない。

### R-15：ライセンスは採用する版・ファイル・ビルド構成で確認する

**根拠:** 03 の 2.2/2.3 節は多くを「要確認」のまま GPL-3.0-or-later 推奨としている。RCD の移植元個別ファイル、データベース・ICC/LUT、FFmpeg 同梱バイナリ等の条件はアプリのライセンス名だけでは決まらない。Rust の依存検査だけでは C/C++・同梱データ・外部実行ファイルを網羅しない。

**改善案:** 依存ごとに版/コミット、取得元、個別 LICENSE とヘッダ、ビルドオプション、配布するバイナリと対応ソース、必要な表記を記録する。GPL-only と or-later を区別し、アプリの選択と整合するか確認する。FFmpeg は `--enable-nonfree` 等の構成を含めて配布条件を確認する。子プロセス化だけを根拠に義務がなくなると判断しない。参照: [FFmpeg のライセンスと配布上の説明](https://ffmpeg.org/legal.html)。

**確認方法:** 最初に移植する RCD ファイルと、実際に同梱する Windows/macOS の FFmpeg 等を対象に一覧を作る。ライセンス方針が決まる前に第三者コードを移植しない。本レビューは個々のコードの法的適合性を確定していない。特許の扱いも GPL の適合と別の未決事項として残す。

### R-16：PoC のクリティカルパスと人の確認時間を見積もる

**根拠:** 05 は M1 を標準 5 週、MVP を並行実施で 23 週とする。PoC-2 → PoC-3 → PoC-5 は、記載工数をそのまま期間とすると 1 + 3〜4 + 2 = 6〜7 週。M0 内で PoC-2 と PoC-1 を始めるため短縮はありうるが、M1 の期間が残工数なのか全 PoC の期間なのかが明確でない。M2/M3 並行も同じ人の週 10 時間のレビュー枠を共有する。

**改善案:** 各 PoC の完了物を M0/M1 のどちらへ計上するか記載し、依存と実際の開始条件から予定を引く。人の必要時間を、サンプル撮影・両 OS 確認・差分画像確認・判断に分ける。PoC の試作と本実装で何を再利用するか決める。全 crate の作成より、1 枚の ARW を開いて色管理表示・書き出しできる縦の経路を優先する。

**確認方法:** M0 の実績で人の確認時間を更新し、M1 後に M2〜M5 を再見積もりする。23 週は到達保証ではなく前提付きの暫定目安とする。A→B の UI 切り替えと、CPU/GPU 二重実装の修正時間を明示する。

### R-17：UI の選定用 PoC に実際の操作と表示条件を追加する

**根拠:** 05 PoC-1 はリサイズ・モニター移動・スライダー・目視の色一致中心。透明 WebView とネイティブ領域の合成では、フォーカス、クリック/ドラッグ、画像座標、倍率変更、IME 等も選定結果を左右する。案 B も名前だけでは色管理・日本語入力が成立する保証にはならない。

**改善案:** 同じテストシナリオで案 A/B を判断する。Windows 100/150/200% と Retina、DPI が違うモニター間移動、ズーム/パン/切り抜き、キーボード、IME、メニュー/ダイアログ、最小化/復帰、GPU 再初期化を含める。MVP の SDR 表示についても HDR が有効な OS での扱いを決める。グリッドの WebView とネイティブ表示の色差の許容条件を書く。

**確認方法:** 両 OS の実機でチェック表と再現手順を残す。単に画像が出たことや高 fps だけで UI の選定を完了しない。

### R-18：撮影日時の原値と推定情報を残す

**根拠:** 04 の 3.1 節は UTC と元のタイムゾーンを持つが、タイムゾーンなしの値は既定タイムゾーンとみなす。カメラ写真も情報がない場合があり、撮影地変更や夏時間で UTC の推定が変わる。v1 の時計修正では後から元の値が必要になる。

**改善案:** 元の日時文字列、元のオフセットの有無、推定に用いたタイムゾーン、補正値、補正後 UTC を区別して保持する。未知の日時を現在時刻に置き換えず、並べ替え時の扱いを書く。

**確認方法:** タイムゾーンなしの ARW/動画、夏時間の重複時刻、機材時計のずれ、日時欠落を用いて、一括修正と取り消しを確認する。

### R-19：処理順序・参照・集計単位を統一する

**根拠:**

- 03 PoC-3 は「デモザイク → WB」、04 と 05 は「WB → デモザイク」。計算順序が結果へ影響するので、実装時の正を統一する。
- 04 の 1.5 節に最新要求の扱いの参照「7.2 節」があるが、該当説明は 6.2 節。2.5 節の `version` 引数と 7.1 節のトレイト例も表現が揃っていない。
- 50 万件の単位とキャッシュの単位は asset/variant で統一が必要。写真と動画の混在日時順は MVP ストーリーにあり、ORG-01 の v1 との差は時刻補正等だと明記した方がよい。
- 2560px の 3:2 画像は約 4.37M 画素、2560×1440 は約 3.69M 画素。どちらもありうるが、計測解像度を固定しないと性能比較がずれる。

**改善案:** 処理順序と仕様の参照元を一つにし、他資料から参照する。性能結果に実寸を記録する。01 の集計は機能行を再集計し、37/44/25/6 の合計 112 件、および難易度 4 以上の集計が一致することを確認済み。集計自体の修正は不要。

## 4. このまま進めてよい点

- **UI から独立した Rust コアと CLI**: UI の選定変更、テスト、自動検証に向く。
- **CPU 基準実装と GPU 実機比較**: 画質の基準を持つ方針はよい。許容差とリリース判定を補えば使える。
- **asset/variant 分離と写真・動画の共通登録**: 仮想コピーと混在一覧を自然に表現できる。
- **カタログと再生成可能キャッシュの分離**: 原本と編集情報を守りつつキャッシュを捨てられる。
- **優先度・キャンセル・世代を持つ非同期処理**: 方向はよい。プロセス間制御と成果物の公開条件を補う。
- **Tauri を暫定候補にして実機で判断**: 主観的スコアだけで固定しない方針はよい。
- **Lightroom 互換やクラウド同期を求めない**: 実装範囲を抑えられる。XMP の往復互換を追加する必要はない。

## 6. 先行 OSS から学ぶこと

- **darktable**: シーン参照の処理を可能な限り線形空間に保ち、表示用の圧縮を後段に置く考え方と、処理順序が結果を変える点を参考にする。GenzoParis では「同じ UI 項目なら順序を自由に替えられる」と扱わず、パイプラインと色空間を固定した契約にする。参照: [darktable の pixelpipe とモジュール順序](https://docs.darktable.org/usermanual/development/en/darkroom/pixelpipe/the-pixelpipe-and-module-order/)。
- **RawTherapee**: デモザイク方式には被写体による得失があるため、RCD 採用を名前や単一チャートだけで決めず、細線・星・偽色・高感度の比較を残す。最初は RCD 一方式に絞り、実サンプルで不足が出た場合に追加する。参照: [RawPedia Demosaicing](https://rawpedia.rawtherapee.com/Demosaicing)。
- 先行 OSS の機能数や内部構造を丸ごと再現しない。特に広範な GUI、複数デモザイク、ML 基盤、全 v1 テーブルを最初から完成させるより、現在の二機種で一枚を正しく扱う経路を先に検証する。
- コード移植は設計を学ぶことと分ける。採用する具体的なファイル・コミット・ライセンスを確認してから行う。
